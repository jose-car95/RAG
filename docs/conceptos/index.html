1. ¿Por qué una base de datos y no ficheros?

Nuestro índice tendrá unos 18.900 chunks (17.183 de código y 1.759 de documentación). De cada uno guardamos cuatro datos: el fichero, la posición inicial, la posición final y el texto.

Con ficheros sueltos tendríamos que cargarlo todo en memoria al arrancar cada comando y recorrerlo entero para cada pregunta. Una base de datos nos da tres cosas:

  • Consultas: pedir «los chunks de este fichero» sin leer los 18.900.
  • Tipos y reglas: la base de datos rechaza un chunk sin ruta o con un índice que no es un número.
  • Escrituras seguras: si el indexado se corta a mitad, no queda un fichero medio escrito (ver transacciones).
Nuestra decisión (registrada el 2026-09-13): SQLite con el módulo sqlite3 de la librería estándar, sin ORM, y escribiendo el SQL a mano para poder explicarlo. El índice será un único fichero: data/processed/index.db.

2. Anatomía: tabla, fila, columna, esquema

Una tabla es una hoja de cálculo con reglas: cada columna tiene un nombre y un tipo, y cada fila es un dato completo. La descripción de las tablas y sus columnas se llama esquema (schema).

Los tipos que usa SQLite son pocos y simples: INTEGER (números enteros), TEXT (texto), REAL (decimales) y BLOB (datos binarios).

3. Claves: primaria y ajena

La clave primaria (primary key) es la columna que identifica cada fila sin repetirse, como el DNI. En SQLite, INTEGER PRIMARY KEY se rellena sola: 1, 2, 3…

La clave ajena (foreign key) es una columna que apunta a la clave primaria de otra tabla. Sirve para no repetir datos: si guardáramos la ruta del fichero en cada uno de los 18.900 chunks, esa ruta larga se repetiría cientos de veces.

Si guardar la ruta en cada chunk (una tabla) o separar files y chunks (dos tablas con clave ajena) es justo una de las decisiones del slice #20. Las dos son defendibles: una tabla es más simple; dos ocupan menos y evitan repetir texto. Se eligió una sola tabla chunks con la ruta repetida. Desde el bonus de indexado incremental (#87) existe también una tabla files, pero sin clave ajena: guarda la ruta y la huella SHA-256 de cada fichero para saber qué cambió.

4. SQL: las cinco frases que necesito

SQL (Structured Query Language) es el idioma para hablar con la base de datos. Con estas cinco frases se hace el 95% del trabajo.

Crear la tabla

CREATE TABLE IF NOT EXISTS chunks (
    id                    INTEGER PRIMARY KEY,
    file_path             TEXT    NOT NULL,
    first_character_index INTEGER NOT NULL,
    last_character_index  INTEGER NOT NULL,
    text                  TEXT    NOT NULL
);

NOT NULL significa «esta columna no puede quedar vacía». Es la base de datos protegiendo el invariante, igual que hace pydantic en el dominio.

Insertar filas

INSERT INTO chunks (file_path, first_character_index, last_character_index, text)
VALUES (?, ?, ?, ?);

Los ? son huecos que se rellenan al ejecutar. Nunca se pegan los valores dentro del texto del SQL: ver inyección SQL.

Consultar con condición

SELECT first_character_index, last_character_index
FROM chunks
WHERE file_path = ?
ORDER BY first_character_index;

SELECT elige columnas, FROM la tabla, WHERE filtra filas y ORDER BY ordena. Con LIMIT 10 te quedas con las diez primeras: eso será nuestro top-k en M3.

Juntar dos tablas

SELECT files.path, chunks.first_character_index
FROM chunks
JOIN files ON files.id = chunks.file_id
WHERE files.path LIKE '%lora.md';

Un JOIN («unir») empareja filas de dos tablas por una condición, normalmente la clave ajena. Es cómo se «deshace» la separación del apartado anterior.

Actualizar y borrar

UPDATE chunks SET text = ? WHERE id = ?;
DELETE FROM chunks;              -- vacía la tabla: reindexar desde cero

5. Consultas parametrizadas e inyección SQL

Tentación: construir el SQL pegando texto.

# MAL: pega el valor dentro del SQL
cursor.execute(f"SELECT * FROM chunks WHERE file_path = '{path}'")

# BIEN: el valor viaja aparte, en una tupla
cursor.execute("SELECT * FROM chunks WHERE file_path = ?", (path,))
Por qué importa. Si path valiera x' OR 1=1; DROP TABLE chunks; --, la primera versión ejecutaría dos órdenes: una consulta que devuelve todo y otra que borra la tabla. Eso es una inyección SQL: el dato se convierte en código. Con ?, la base de datos trata ese texto como un valor, nunca como SQL.

En nuestro proyecto el «atacante» sería inocente: una ruta con un apóstrofo o una pregunta del usuario con comillas bastaría para romper la consulta. La forma correcta es también la más cómoda, así que no hay excusa. Ojo al detalle de la coma en (path,): sin ella no es una tupla.

6. Transacciones

Una transacción agrupa varias escrituras en un «todo o nada» (atomicidad). O se guardan todas, o no se guarda ninguna. Si el indexado se corta con Ctrl+C a mitad, no queda un índice con la mitad de los chunks.

Y hay un efecto práctico enorme: velocidad. Sin transacción explícita, SQLite confirma en disco cada INSERT; con una sola transacción para los 18.900 chunks, confirma una vez. La diferencia suele ser de dos órdenes de magnitud, y nosotros tenemos un límite de 300 segundos.

with sqlite3.connect(index_path) as connection:   # una transacción
    connection.executemany(
        "INSERT INTO chunks (file_path, first_character_index, "
        "last_character_index, text) VALUES (?, ?, ?, ?)",
        rows,                                     # 18.900 tuplas
    )
# al salir del with: COMMIT si todo fue bien, ROLLBACK si hubo excepción

COMMIT es «confirma los cambios» y ROLLBACK es «deshazlos». Fíjate en que la conexión es un context manager, como el open del slice #4: el mismo patrón que exige el enunciado para no dejar recursos abiertos.

7. Índices de base de datos (y el choque de nombres)

Cuidado con la palabra «índice». En RAG, el índice es toda la estructura de búsqueda que construimos. En bases de datos, un índice es un atajo para encontrar filas rápido. Son cosas distintas con el mismo nombre.

Sin índice, para responder WHERE file_path = '…lora.md' la base de datos recorre las 18.900 filas una por una: es un escaneo completo (full scan). Con un índice sobre esa columna, salta directamente a las filas que valen.

Para ver si una consulta usa el índice o escanea, SQLite tiene una orden muy útil: EXPLAIN QUERY PLAN SELECT …. Dice, en texto, qué plan va a seguir.

1. El problema: de una pregunta a cinco fragmentos

Tenemos 18.942 chunks (fragmentos de texto) guardados en SQLite. Llega una pregunta escrita por una persona:

What HTTP endpoint is used to dynamically load a LoRA adapter in vLLM?

Y la respuesta correcta, según el dataset público, está en un sitio concreto del corpus:

data/raw/vllm-0.10.1/docs/features/lora.md  [4695:6098]

Nuestro trabajo en M3 es devolver ese fragmento entre los 5 primeros resultados. Ni más ni menos. El modelo de lenguaje llegará en M5 y solo sabrá redactar con lo que le demos: si la recuperación falla, la respuesta será mala por muy bueno que sea el modelo. Por eso M3 es el corazón del proyecto.

Búsqueda léxica (lexical search, de lexis, «palabra» en griego) significa buscar por las palabras que aparecen escritas, no por el significado. Si la pregunta dice «endpoint» y el documento dice «endpoint», hay coincidencia. Si la pregunta dice «endpoint» y el documento dice «URL de la API», la búsqueda léxica no los relaciona: para eso harían falta embeddings (representar el significado como una lista de números), que son el bonus del proyecto, no lo obligatorio.

La idea de fondo, y es más simple de lo que parece: si comparten palabras, probablemente hablan de lo mismo. Todo lo demás de esta página son refinamientos de esa frase.

2. Tokenizar: de texto a palabras comparables

Tokenizar (to tokenize, de token, «ficha») es partir un texto en las piezas que vas a comparar. Cada pieza es un token. Suena trivial y no lo es, porque hay que decidir qué cuenta como una pieza.

La analogía: imagina que quieres saber si dos cestas de la compra se parecen. Antes de comparar tienes que ponerte de acuerdo en qué es «un artículo». ¿Son lo mismo «tomate» y «Tomates»? ¿Y «tomate frito» es uno o son dos? Si cada uno cuenta a su manera, la comparación no significa nada. Tokenizar es fijar esas reglas, y lo importante es aplicar las mismas a la pregunta y al corpus.

Las decisiones que tenemos delante en el slice #22:

3. El índice invertido

Con la pregunta ya en 7 palabras, la pregunta obvia es: ¿comparo esas palabras con los 18.942 chunks, uno por uno? Funcionaría, pero es trabajo tirado a la basura: la mayoría de los chunks no contienen ninguna de las palabras.

Un índice invertido (inverted index) es un diccionario que va de la palabra a los documentos donde aparece. Se llama «invertido» porque el orden natural es el contrario: un documento contiene palabras. Aquí le damos la vuelta.

La analogía es el índice del final de un libro de texto: en vez de leer las 600 páginas buscando «mitocondria», vas al índice, encuentras «mitocondria: 41, 88, 203» y abres tres páginas. Las páginas que te da el índice para una palabra se llaman su posting list (lista de apariciones).

Dos números que salen de ahí y que hay que saber explicar:

  • Con la unión de las listas (chunks con al menos una palabra) puntúas 4.972 en vez de 18.942 para esta pregunta de siete palabras.
  • Con la intersección (chunks con todas las palabras) queda exactamente 1 chunk... y resulta ser el correcto. Tentador, pero es una trampa: exigir todas las palabras deja muchísimas preguntas sin ningún resultado. Por eso se usa la unión y se ordena con una puntuación, en vez de filtrar.
Cuidado con el número de candidatos: 4.972 es esta pregunta, no la norma. Medido sobre las 199 preguntas reales de los datasets públicos, la mediana es de 13.731 candidatos de 18.942, o sea el 72% del corpus (mínimo 5.014, máximo 17.014). Es lógico: una pregunta tiene 13,6 palabras de media, y basta con que una aparezca para que el chunk entre en la lista.

Así que el índice invertido no se gana el sueldo descartando chunks. Se lo gana por dos otras razones: te da df ya contado para IDF, y te ahorra volver a tokenizar 1,8 millones de tokens en cada consulta. Medido: construirlo una vez cuesta 1,22 s y responder a las 199 preguntas con él ya montado, 1,75 s (9 ms por pregunta).

4. TF: contar apariciones (y por qué no basta)

TF es term frequency, «frecuencia del término»: las veces que una palabra aparece en un documento. La intuición es razonable: si «adapter» sale 13 veces en un fragmento, ese fragmento habla de adaptadores.

Pero contar y ya lleva a errores. Estos dos chunks son reales, de nuestro índice, y ambos hablan de LoRA. El segundo es un señuelo (decoy, el pato de plástico del cazador): un candidato que se parece mucho al bueno y no lo es, elegido a propósito para comprobar que la puntuación no se deja engañar por la repetición.

5. IDF: las palabras raras informan más

IDF es inverse document frequency, «frecuencia inversa de documento». Es un peso por palabra: cuanto en menos documentos aparece una palabra, más informa cuando aparece.

La analogía: en una fiesta de 200 personas, que alguien diga «llevo zapatos» no te ayuda a encontrarlo; que diga «llevo un sombrero verde» te lleva directo. «Zapatos» tiene IDF bajo, «sombrero verde» IDF alto. Y esto explica por qué las stop words no hacen falta tratarlas aparte: the aparece en casi todos los documentos, así que su IDF es casi cero y se anula sola.

La fórmula que usa BM25, con N = número de documentos y df = en cuántos aparece la palabra:

IDF(palabra) = ln( (N - df + 0.5) / (df + 0.5) )
Cambio del slice #48 (2026-10-13): usamos la IDF original de Robertson. Antes llevábamos un 1 + dentro del logaritmo, que es la variante de Lucene. Con la original, una palabra que está en la mitad o más de los chunks daría 0 o un número negativo, y entonces un chunk bajaría por contener una palabra de la pregunta. Solo le pasa a def (en 11.369 de 18.942 chunks: daría −0,41). Por eso, si el resultado no es positivo, usamos un suelo diminuto, IDF_FLOOR = 1e-6 (una millonésima, el mismo que usa SQLite): la palabra casi no cuenta, pero sigue desempatando.

El ln es el logaritmo natural: aplasta las diferencias grandes. Sin él, una palabra 100 veces más rara pesaría 100 veces más, y eso desequilibra la cuenta. Los 0.5 son un suavizado (smoothing): evitan dividir por cero y que el resultado se vaya al infinito con palabras rarísimas.

6. TF-IDF: el producto de los dos

TF-IDF multiplica las dos ideas: cuántas veces aparece (TF) por cuánto informa esa palabra (IDF). Se suma para todas las palabras de la pregunta y eso da la puntuación del documento:

puntuación(pregunta, chunk) = suma sobre cada palabra de [ TF(palabra, chunk) × IDF(palabra) ]

Es un salto enorme respecto a contar a pelo, y ya resolvería nuestro ejemplo. Pero le quedan dos defectos, y BM25 existe precisamente para arreglarlos.

Defecto 1: la décima aparición cuenta lo mismo que la primera

Con TF-IDF, un chunk con 20 veces «lora» puntúa el doble que uno con 10. ¿De verdad habla el doble de LoRA? No: pasar de 0 a 1 aparición es un salto informativo gigante (el tema aparece), y pasar de 19 a 20 no dice casi nada.

Defecto 2: los documentos largos hacen trampa

Un texto largo contiene más palabras de todo, así que acumula más TF por el simple hecho de ser largo. Sin corregirlo, la búsqueda se inclina hacia los fragmentos grandes aunque hablen del tema de pasada.

7. BM25: dos arreglos sobre TF-IDF

BM25 significa Best Matching 25: fue el vigesimoquinto experimento de una serie de investigación de los años 90, y es el que quedó. Hoy sigue siendo la referencia de la búsqueda léxica: es lo que hay dentro de buscadores como Lucene o Elasticsearch.

La fórmula completa, por cada palabra de la pregunta:

BM25(palabra, chunk) = IDF(palabra) × [ tf × (k1 + 1) ] / [ tf + k1 × (1 - b + b × dl / avgdl) ]

Da respeto, pero solo tiene cinco ingredientes, y tres ya los conoces:

SímboloQué esEn nuestro proyecto
tfVeces que la palabra aparece en el chunkSe cuenta al indexar
IDFPeso de la palabra, lo de la sección anteriorSale de df y N=18.942
dldocument length: longitud del chunk en tokensEntre 0 y 404
avgdlaverage document length: longitud media96,5 tokens
k1, bLos dos mandos que ajustan la fórmulaLos de la definición original de Okapi BM25: k1=1.2, b=0.75 (hasta el slice #48 usábamos k1=1.5)

El mando k1: saturación

Saturación (saturation) es que las aportaciones dejen de crecer a partir de cierto punto. La analogía: el primer vaso de agua con sed te salva; el sexto ya casi no aporta. k1 decide a qué velocidad se llega a ese techo. Con k1 pequeño la curva se aplana en seguida (solo importa si la palabra está o no); con k1 grande se parece más a contar linealmente.

El mando b: normalización por longitud

Normalizar es poner cosas de distinto tamaño en una escala comparable. Aquí se compara la longitud del chunk (dl) con la media (avgdl): si el chunk es más largo que la media, sus apariciones valen algo menos; si es más corto, algo más.

b decide cuánto se aplica esa corrección: con b=0 se ignora la longitud, con b=1 se corrige del todo. El b=0.75 habitual es un punto intermedio.

9. Los dos mandos, en números

La fórmula tiene dos valores que elegimos nosotros, k1 y b, y conviene saber de dónde salen: no se deducen de ninguna matemática. Son empíricos. En los años 90, el equipo que desarrolló BM25 probó la fórmula contra colecciones de documentos de referencia y buscó qué valores funcionaban bien en muchas colecciones distintas. El consenso que quedó es k1 entre 1,2 y 2,0 y b alrededor de 0,75. Tanto, que Lucene y Elasticsearch, los dos motores de búsqueda más usados, vienen de fábrica con k1=1.2 y b=0.75. Nuestro 1,5 está dentro del rango habitual.

10. Recall@k e IoU: cómo se nos mide

Recall@k (recall, «recuperación» o «exhaustividad») responde a: de las fuentes correctas, cuántas he traído entre mis k primeros resultados. Si una pregunta tiene 2 fuentes buenas y devuelvo 5 chunks entre los que están las 2, el recall de esa pregunta es 1,0; si solo encuentro una, es 0,5. El recall del dataset es la media de todas las preguntas.

Lo que nos exige el enunciado con k=5:

DatasetRecall@5 mínimoPor qué es más fácil o difícil
Documentación (.md)≥ 0,80 La pregunta y la respuesta usan el mismo vocabulario en prosa
Código (.py)≥ 0,50 La pregunta está en inglés y la respuesta es código: hay menos palabras compartidas

Y falta una pieza: ¿cuándo se considera que un chunk mío «es» la fuente correcta? No puede ser coincidencia exacta de caracteres, porque nuestros cortes nunca caerán justo donde los puso quien hizo el dataset. Se usa el IoU (Intersection over Union, «intersección sobre unión»): se miden los dos rangos de caracteres y se divide lo que comparten entre todo lo que ocupan juntos.

El umbral es 0,05, y es generoso a propósito. Basta con que nuestro chunk se solape un 5% con la fuente para que cuente como acierto. Es decir: el chunking no tiene que ser perfecto, tiene que contener la respuesta. Lo que de verdad decide la nota es el orden que da BM25.

1. El diagnóstico: buenos chunks, mal ordenados

Al clasificar los fallos a Recall@5, la mayoría no eran fuentes imposibles de encontrar: el chunk correcto estaba en el ranking, pero en los puestos 6 a 200. En code, 28 de 36 fallos; en docs, 13 de 17. El problema era el orden, no el tamaño del chunk.

La causa en code: las preguntas nombran clases como Molmo o DeepSeek, pero el código las escribe pegadas (MolmoForCausalLM), y el tokenizador las dejaba como un solo token que nunca coincide con molmo. Y un chunk a mitad de una clase había perdido el nombre de la clase a la que pertenece.

2. CamelCase: partir MolmoForCausalLM

CamelCase = palabras pegadas con mayúscula inicial. Encima del corte por guion bajo que ya teníamos, ahora partimos también en los saltos de mayúscula. El token entero se conserva, y se añaden las partes:

MolmoForCausalLM → molmoforcausallm, molmo, for, causal, lm

Los dígitos no parten un token. int8 y fp8 siguen enteros (son nombres de técnicas, decisión del 2026-09-29). Solo parten los cambios de mayúscula/minúscula, no la frontera letra-dígito.

3. Contexto del chunk: clase, títulos y ruta

Cada chunk se guarda con un contexto: unas palabras extra que la búsqueda tokeniza junto al texto, pero que nunca se devuelven como fuente (el rango y el texto del chunk no cambian, así que la IoU no se toca). El contexto es:

1. La cadena completa de search

Esto es lo que ocurre, en orden, al escribir uv run python -m src search "How to configure OpenAI server?" --k 5:

  1. python -m src hace que Python ejecute src/__main__.py, que es lo que convierte la carpeta en un programa ejecutable.
  2. __main__.py llama a sys.exit(main()): el número que devuelva main será el código de salida del proceso.
  3. main(), en src/bootstrap.py, crea RagCli con los adaptadores de salida reales (SqliteIndexStore, FileCorpus, JsonDatasetStore, load_generator) y devuelve run(...) con esa instancia ya montada.
  4. run() es la frontera de errores: envuelve la llamada a Fire en un try. Aquí se decide que ninguna excepción salga como traceback y que un fallo valga salida 1.
  5. Fire mira la primera palabra (search), encuentra el método con ese nombre, asigna el texto a query por posición y --k 5 a k, adivinando el tipo. Traduce, no valida.
  6. RagCli.search llama a run_search(query, k, index_path, self._index_store). Es lo único que hace, además de imprimir.
  7. run_search (aplicación) valida k y la query, y entonces pide las filas a load_chunks.
  8. load_chunks (adaptador de salida SqliteIndexStore, a través del puerto IndexStore) comprueba que el fichero existe, abre SQLite, lanza el SELECT y devuelve las filas.
  9. run_search tokeniza el texto de cada chunk con tokenize, construye el índice invertido con build_index, se guarda un diccionario de id → (file_path, first, last), y llama a rank con los tokens de la query.
  10. rank (dominio) usa idf, K1 y B, ordena y corta a k. Devuelve parejas (chunk_id, puntuación).
  11. run_search convierte cada id en un MinimalSource con el diccionario de metadatos y devuelve parejas (MinimalSource, puntuación).
  12. RagCli.search imprime una línea por pareja, o No sources found. si la lista está vacía. run devuelve 0 y sys.exit lo entrega al sistema.
La frase corta para la defensa: «la CLI traduce e imprime, la aplicación coordina y valida las reglas del enunciado, el dominio calcula sin tocar disco, y un solo adaptador de salida sabe de SQLite».

2. Por qué el adaptador de salida comprueba el fichero antes de conectar

Porque sqlite3.connect crea el fichero si no existe. Medido:

¿existe el fichero antes?  False
al consultar: OperationalError: no such table: chunks
¿existe el fichero DESPUÉS? True (0 bytes)

Si conectáramos primero, pasarían dos cosas malas a la vez: dejaríamos un index.db vacío de 0 bytes en el disco de quien nos corrige, y el mensaje hablaría de una tabla que falta, que es jerga interna, en vez de decir lo único útil: ejecuta index primero.

Así que la comprobación es una cláusula de guarda: va primero, corta antes de hacer nada, y deja el disco como estaba.

Y por qué list(...) y no lo que devuelve execute

Un cursor de SQLite es perezoso: va trayendo las filas a medida que las recorres. Pero la conexión se cierra al salir del with closing(...), así que quien reciba el cursor intentaría leer de una conexión ya cerrada:

devolviendo el cursor -> ProgrammingError: Cannot operate on a closed database.
devolviendo list(...)  -> [(1,), (2,)]

list(...) fuerza a leer todas las filas mientras la conexión sigue abierta. Aquí la lista no es pereza: es la única opción correcta sin dejar la conexión abierta a merced de quien llame.

3. Quién valida qué, y por qué no todo en el mismo sitio

run_search valida k y la query, pero no valida index_path. No es un olvido: cada comprobación vive donde está el conocimiento para hacerla.

Qué se validaDóndePor qué ahí

3. Las dos flechas: quién llama y quién conoce

Aquí se confunde casi todo el mundo. Detrás de cada dibujo de arquitectura hay dos tipos de flecha:

FlechaPregunta que respondeDónde se ve
De dependencia¿Quién conoce a quién? En los import del código
De llamada¿Quién llama a quién al ejecutar? En lo que pasa cuando el programa funciona
AL EJECUTAR (llamadas, hacia fuera):
  CLI  ──►  run_search  ──►  SQLite                 la cocina abre la nevera

EN EL CÓDIGO (imports, hacia dentro):
  CLI  ──►  run_search  ──►  IndexStore (puerto)  ◄──  SqliteIndexStore
                       └──►  dominio  ◄──────────────────────┘

run_search llama a SQLite, pero no lo conoce: solo conoce el puerto. SqliteIndexStore conoce el puerto (para encajar) y el dominio (para devolver sus datos). Que la llamada vaya hacia fuera y el import hacia dentro tiene nombre: inversión de dependencias (dependency inversion).

Lo que estaba mal antes del #61: retrieval.py hacía from ...sqlite_index import load_chunks. El libro de recetas nombraba la marca de la nevera. Eso es arquitectura por capas, no hexagonal, y un evaluador que sepa del tema te lo podría señalar si la llamabas hexagonal.

Cuatro ficheros, cuatro papeles. Sigue find_files de uno a otro:

El adaptador de salida: la implementación real

# src/adapters/outbound/corpus.py
class FileCorpus(CorpusReader):
    def find_files(self, raw_directory: str) -> list[Path]:
        corpus_root = Path(raw_directory)

El montaje: quién va en ese enchufe

# src/bootstrap.py

Los nombres no coinciden, y es a propósito. El puerto se llama por lo que hace (CorpusReader, «lector del corpus»). El adaptador se llama por cómo lo hace (FileCorpus, «corpus en ficheros»). Mañana podría haber un CachedCorpus, y también sería un CorpusReader.

5. Los puertos son Protocol

Un Protocol (de typing) describe una forma: qué métodos hay y con qué firma. Un objeto encaja si tiene esos métodos, herede o no del puerto. Esto se llama tipado estructural (structural typing): «si camina como un pato, es un pato», pero comprobado por mypy.

  • En el caso de uso, el tipo del parámetro es siempre el puerto (corpus: CorpusReader), nunca el adaptador. Si pusieras FileCorpus, el caso de uso volvería a conocer la marca y test_architecture.py fallaría.
  • En el adaptador escribimos la herencia de forma explícita (class FileCorpus(CorpusReader)). No hace falta para que funcione, pero así ves el enlace al abrir el fichero, y mypy revisa la clase entera aunque nadie la use todavía.

¿Basta con implementar uno de los métodos? No.

Prueba ejecutada con un puerto Aparato de tres métodos y clases que solo tienen uno:

CasoPython al ejecutarmypy (gate de tipos)
Sin herencia, 1 de 3 métodos Funciona hasta que llamas al que falta ❌ "SoloEnciende" is missing following "Aparato" protocol members: apagar, limpiar
Con herencia, 1 de 3 métodos Peor: el método que falta devuelve None en silencio (heredó el ... vacío) ❌ Cannot instantiate abstract class "SoloApaga" with abstract attributes "encender" and "limpiar"

Python solo no te protege: te protege mypy. Si dos aparatos solo hacen una cosa cada uno, eso son dos puertos, no uno a medias (segregación de interfaces).

6. bootstrap.py: monta y se aparta

No es un gestor que esté en medio mientras el programa funciona. Actúa una vez, al arrancar, como el electricista que instala los aparatos antes de abrir el restaurante y se va.

uv run python -m src search "..." --k 5

1. __main__.py        sys.exit(main())                         → bootstrap.main()
2. bootstrap.main()   build_cli(): crea SqliteIndexStore(), FileCorpus(),
                      JsonDatasetStore() y RagCli(...)           ← aquí se enchufa todo
                      run(cli)                                   ← y se aparta
3. run()              frontera de errores: try alrededor de Fire
4. Fire               "search" → RagCli.search(query, k)
5. RagCli.search      run_search(query, k, index_path, self._index_store)
6. run_search         index_store.load_chunks(...)  → el SqliteIndexStore real
  • Es el único fichero que escribe SqliteIndexStore() o FileCorpus(). Cambiar un aparato es cambiar una línea aquí.
  • RagCli guarda los adaptadores en atributos con _ (self._corpus...) para que Fire no los liste como comandos.
  • Con el bonus de la API habría una segunda función, build_api(), que montaría los mismos adaptadores de salida con otro adaptador de entrada. La página web del chat hablaría con esa API por la red; bootstrap no la llama.

8. DDD, hexagonal, cebolla y limpia

No son rivales: son la misma idea con distintos nombres. Todas cumplen la regla de dependencia: los imports apuntan hacia el dominio y el dominio no conoce ni SQLite ni la terminal.

AñoNombreAutorSu vocabulario
2003Capas de DDD (Domain-Driven Design, «diseño guiado por el dominio»)Eric EvansUI, application, domain, infrastructure
2005Hexagonal (Ports and Adapters)Alistair Cockburnnúcleo, ports, adapters de entrada y de salida
2008Cebolla (Onion)Jeffrey Palermodomain, services, infrastructure
2012Limpia (Clean Architecture)Robert C. Martinentities, use cases, interface adapters, frameworks
  • DDD no es sobre todo una arquitectura: es diseñar el software alrededor del problema real. De paso propone cuatro capas, y de ahí viene la palabra «infrastructure».
  • «Infrastructure» (DDD, limpia) y «adaptador de salida» (hexagonal) son la misma pieza con distinto nombre. Elegimos la hexagonal pura para no mezclar vocabularios: si la llamas hexagonal, que lo diga la carpeta.
  • inbound / outbound = de entrada / de salida (driving / driven en los libros). No in / out: in es palabra reservada de Python y from src.adapters.in.cli import … da SyntaxError (probado).

9. El test que vigila la regla

tests/test_architecture.py lee los import de cada fichero de src/ con ast y falla si una capa importa lo que no debe:

Un regalo de los puertos en los tests: para comprobar que search_dataset carga el índice una sola vez ya no hace falta «parchear» nada. Se enchufa un CountingStore que cuenta las llamadas a load_chunks, y el test mira que sea 1.
